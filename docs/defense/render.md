### 模块：输出渲染 `src/render.ts`

**1. 这段在干什么（一句话）**
把判定结果渲染成两种形态 —— 给人/AI 看的**冲突视图**（严重度 + 变更点 + 来源当前内容 + 下一命令建议）与 `--json` 单行结构化输出；并提供 `--plain` 的"只出正文"。

**2. 关键设计决策 + 为什么这么做**

- **默认冲突视图，`--plain` 只出正文，`--json` 给结构。** 三者对应三类消费者：人（看冲突）、AI（要正文）、脚本/`jq`（要结构）。题面"默认冲突视图，可切换为只出正文"直接落成默认 + `--plain`（别名 `--body`），且 `--plain` 与 `--json` 互斥。
- **`error` 档不回显任何旧文字**：`currentSource=null`，渲染时打印"当前内容 已刻意隐藏（引用目标已不在…）"，并**必给追查入口** `gmd log <doc> --path <src>`。这是题面阶段 2 完成标志——"对一个失效引用给出原因与追查入口，AI 无需自己调用 Git"。
- **`warning` 档把"变更点 + 来源当前内容"摆出来、工具不猜**：题面"warning 是唯一需要 AI 解释的一档"。渲染只陈列事实（哪几行变了、现在的源码长什么样），**不加判断性措辞**，把决定权留给 AI。
- **`--json` 单行、字段与契约逐一对齐**：`read → {doc, blocks}`、`log → 数组`、`commit → {block,rev,text_hash,range}`、`edit → {draft_path}`；失败时 `{"error","code"}`，**人类可读文字一律走 stderr**，保证 stdout 永远是"可直接 `JSON.parse` 的干净数据"（下面再给兄弟命令都不行）。
- **两处"仅在条件成立时附加"的可选字段**：`read` 的 `changes_omitted`（`changes` 被 20 条上限截断时）与 `log --block` 的 `note`（该版本带 `note` 时）。**为什么 `note` 必须进 `--json`**：`--allow-dirty` 写下的 `based_on_dirty` 是"此版本基于未提交来源"的审计标记（§4.6.2 的要求）。只在人类可读视图里显示的话，**用 `--json` 的 AI 就分辨不出版本来源是否干净** —— 审计标记必须机器可读。两者都不改变无条件时的形状（无 `note` 的版本不会凭空多出字段）。
- **`--version` 现在渲染**该版本当时写下的正文**（阶段 4·3）**：`hist[].text` 里存着每一版的正文，所以 `read --version <rev>` 给出"正文 + 来源信息"、`--plain --version <rev>` 只出该版正文。历史版本本身不谈严重度，因此额外打印一行**该块当前严重度（`active_severity`）**并写明"针对活动版本"—— 参考接口说 `read --version` 要"取正文与严重度"，严重度始终是对**活动版本**的判断，把名字标清楚就不会被误读成 rev 的属性。旧格式缺正文时给 `text: null` / stderr 说明，**不改退出码**。
- **`versionToJson` 刻意**不含 `text`**：它同时服务 `log --block --json`。`log` 是"查账"（版本元数据一览），把每版正文都塞进去会让输出随历史线性膨胀，也改变了既有的 key 形状（用例 19 有断言）。要取某一版的正文就用 `read --version <rev> --json` —— **"查账"与"取正文"分成两条命令**，各自契约稳定。
- **`--plain` 的失效提示走 stderr（阶段 4 收口）**：`--plain` 不带严重度标记，而 `error` 档的动作是"必须重写"——只给退出码 3，AI 在多块文档里不知道失效的是哪一块，这正是"补丁式改一段已经不适用的文字"的入口。所以 stdout **严格保持纯正文**（"只出正文"是参考接口的承诺），把"哪几块失效 + 下一步命令"放到 stderr；`--block` 窄化时若失效的是别的块也提醒一句。退出码仍按整篇文档算。

**3. 可能被追问的问题 + 要点**

- **Q：为什么 `error` 偏偏不给旧文字？给出来不是更方便 AI 对比吗？**
  A：题面原话——"error 刻意隐藏旧文字：留着它，AI 就会去补丁式修改，而引用目标已经不在了"。既然引用目标消失/被整段重写，正确的动作是**整段重写**；给出旧文字会诱导 AI 打补丁，产出更差的结果。这是一条**有意的行为约束**。
- **Q：`--plain` 与 `--json` 为什么必须互斥？**
  A：语义冲突——一个要"纯正文"、一个要"结构化元数据"。若同时给，stdout 既不是合法 JSON 也不是纯正文，`jq`/`JSON.parse` 会崩。互斥并退出码 1，错误明确。
- **Q：`--plain` 下为什么仍然沿用退出码 3（存在 error 块）？**
  A：正文与退出码解耦：即便只出正文，脚本仍需知道"这文档里有失效引用"。所以 `--plain` 照常探测判定结果只用于决定退出码，不打印冲突视图。
- **Q：`--json` 失败时为什么还要在 stderr 再打印一句人话？**
  A：两条通道服务两类消费者：stdout 给机器（`{"error","code"}`），stderr 给人（`错误：…`）。既不污染 stdout，又让终端用户看得懂。
- **Q：`log --path` 的降级提示放在哪？**
  A：渲染成 `renderLogPath(..., note)` 的一行 `※ …`，例如"range 超出当前文件行数（当前 N 行），已降级为列出该文件全部提交"。让 AI 明确知道"这不是全部历史、而是降级结果"。
- **Q：`log --block --json` 里为什么要多一个 `note` 字段？PLAN §4.9 的契约里没写。**
  A：这是**附加**字段，只在版本确实带 `note` 时出现（无条件时形状与 §4.9 完全一致，`test/用例 19` 的 key 断言仍然通过）。加它的理由是：§4.6.2 要求 `--allow-dirty` 把 `based_on_dirty` 写进 `note` 并在审计输出里标注。人类可读视图已经打了 `note=based_on_dirty`，但 `--json` 是 AI 的通道 —— 不带上就意味着**AI 分辨不出这一版是基于未提交来源写出来的**，审计链在机器侧断了。同类的先例是 `read` 的 `changes_omitted`。
- **Q：`read --version --json` 里为什么 `text` 缺失给 `null`，而不是像 `note` 那样"没有就不出现"？**
  A：因为这条命令的**主产物就是那个 `text`**。`note` / `changes_omitted` 是边角信息，"字段消失"就够了；而"我要的那一版正文"如果只是字段不见了，调用方分不清是"这版没存"还是"我解析错了键"。所以这里显式给 `null`（类型上就是 `string | null`），配套 stderr 说明原因。**形状稳定性与主产物的确定性，在这里后者优先。**
- **Q：`--plain --version 1` 取不到正文时为什么返回 0 而不是报错？**
  A："这一版没存正文"是**数据事实**（旧格式文件合法存在），不是命令用错、也不是格式损坏。用退出码惩罚它会让脚本把"合法的旧文件"当成失败。正确做法是：stdout 不输出内容（**绝不伪装成空正文**）、stderr 点名是哪一版缺正文、退出码保持 0。用例 32 覆盖。
- **Q：`--plain` 为什么不干脆把失效块的正文也藏起来？**
  A：题面说的是 `error` 时不回显**来源**的旧文字（理由写得很明确："留着它，AI 就会去补丁式修改，而**引用目标已经不在了**"），本项目相应地隐藏 `currentSource`；而 `--plain` 要出的是**文档自己的正文**，藏掉它等于这条命令在最需要它的场景下失效（比如"把失效片段都重写一遍"的流程要先拿到现文）。真正的风险不是"看到旧正文"，而是"**不知道它已失效**"—— 所以补的是**状态信息**（stderr 点名 + 下一步命令），而不是砍掉内容。这也是"两条通道各司其职"：stdout 给内容、stderr 给状态与建议。
