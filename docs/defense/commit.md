### 模块：写回闸门 `src/commit.ts`

**1. 这段在干什么（一句话）**
`gmd commit` 在把"新正文"写回 `.gmd` 之前，先**剥离草稿头**、跑**五道校验**（任一不过则拒绝、退出码 4），通过后重算来源信息、`hist` 追加新版本、用**原子写**落盘。

**2. 关键设计决策 + 为什么这么做**

- **步骤 0 先做：剥离并校验草稿头，定义"新正文"。** 若输入首行是 `<!-- gmd:draft … -->`，丢弃该行并解析 JSON；`doc`/`block`/`base_rev` 与实参或当前状态不符即拒绝。**这一步是必需的**：不剥离的话，① 草稿头会进 `.gmd` 正文、污染格式；② `text_hash` 永远对不上，"内容未变化"校验与用例 18 永远不可达。后续所有 hash/比较/写回**一律针对"新正文"**。
- **五道校验**（顺序即优先级）：
  1. **正文非空**（`trim()` 后非空）；
  2. **base_rev 匹配**（草稿基于当前活动版本）—— 防止覆盖别人的改动；
  3. **dirty 闸门** —— **目标来源**范围内有未提交修改（`isRangeDirtyTexts`，与 §4.3 步骤 3 同一口径）且未加 `--allow-dirty` ⇒ 拒绝"来源存在未提交修改，默认拒绝写入"（题面硬约束 5："不伪造正式版本"，见下条说明为什么不直接复用 `judgeBlock(...).dirty`）；
  4. **内容确有变化** —— `textHash(新正文) === 当前 text_hash` ⇒ 拒绝"内容未变化"（避免造无效版本）；
  5. **引用范围仍然存在** —— `targetRange[1] > countLines(目标来源)` ⇒ 拒绝"引用范围已不存在"（见下条，**这是防止把 `error` 写成 `ok` 的闸门**）。
- **`--path` / `--range`：重新绑定引用（阶段 4·2）**。目标来源 `(targetPath, targetRange)` 缺省沿用活动版本，可用这两个 flag 改指到仍存在的来源。**这是 `error` 档"必须重写"的收尾通路**：旧来源已消失（文件被删 / 整段被替换）时光重写正文没用，`range` 沿用旧值必然越界、只能拒写；改指之后就能写回，新版本记新 `(path, range)`，`hist` 里旧版本各自的 `path`/`range` 一律不动（历史只追加）。**校验 3 与校验 5 因此必须针对 `targetPath/targetRange` 算，而不是拿被判定的旧来源** —— 旧来源已经在这版被放弃了。
- **校验 3 不再调 `judgeBlock(...).dirty`，改用同一组原语直接算**（`showText(HEAD, targetPath)` + `isRangeDirtyTexts(srcText, headText, targetRange)`）。两个原因：① 重绑定后闸门必须落在**新**来源上；② `judgeBlock` 在"正文与元数据不一致"等步骤 0 场景会**提前返回 `dirty=false`**，于是"先把正文手改坏、再 commit"就能在**来源范围有未提交修改**时照样写回 —— 那是题面"引用范围内有未提交修改 ⇒ 不允许写回"的一个绕过口子（用例 30 锁住）。
- **越界闸门（校验 5）为什么必须有**：`range` 在阶段 1–3 只能**沿用旧范围**，而 `hashRange` 对越界范围会**静默截断**：范围全在文件外时切片为空 ⇒ `src_hash` = 空串 sha256。若照写，新版本就变成"引用目标已消失、却自证与当前内容一致"，下一次 `read` 会判 `ok` —— 直接违反题面"引用目标消失 ⇒ `error`，必须重写"和"绝不判为可用"。所以宁可**拒写（码 4）**：本条与判定侧 `judge.ts` 步骤 3.5 是同一件事的两道闸。真正的"重写后写回"需要把引用改指到仍存在的范围（阶段 4 的符号/选区级引用，本实现未做，如实声明）。
- **`--allow-dirty`（阶段 4·1）**：显式放行 dirty 写回，但必须① 在审计输出（stderr）显著标注"此版本基于未提交来源"，② 新版本 `note` 写 `based_on_dirty`。做到"可控 + 可追溯"。
- **通过后 `range` 沿用它记录的旧范围**：阶段 1–3 不做符号/选区级引用（那是阶段 4）。`commit` 只重算 `commit`（`git rev-parse HEAD`）与 `src_hash`（`hashRange(当前文件文本, range)`，**复用 gitrepo 的唯一实现**）。
- **原子写：写 `.tmp` → `rename`**。`rename` 在同一文件系统内是原子的，避免"写到一半崩溃 ⇒ 半截 `.gmd`"。测试专门验证 `.tmp` 不残留（`existsSync(doc+'.tmp') === false`）。
- **来源在写回时已取不到 ⇒ 同样拒绝（码 4），理由必须可解释**：`readSourceForCommit` 把 `ENOENT` / 非 UTF-8 转成 `CommitRejected`。**不能让裸 `ENOENT` 冒泡** —— 那会被 CLI 的兜底分支映射成码 1「参数/用法错误」，而参数明明是好的，调用方据码分支就会误判。这是题面 §2.4"文件没了 ⇒ `error` ⇒ 必须重写"的收尾：AI 重写得了正文，但阶段 1–3 的 `range` 只能沿用旧范围 ⇒ **记不了新版本的来源** ⇒ 只能明确拒绝。恢复来源文件后同一条草稿即可正常写入。
- **只改目标块（结构性保证）**：`serializeGmd(raw, blocks, [目标块 id])` **只重写目标片段**，其它片段与文档头按原文**逐字节拷贝**（`hist` 用 `[...b.hist, version]`，**只追加**）。这样"改一个块"不会顺手改写别的块的元数据行（键序、扩展字段都原封不动）。目标块自己的扩展字段用 `{ ...b }` 展开带走（`EXTRAS` 是 Symbol 键，展开才带得走），写回时由 `renderBlockHead` 合并回去 —— 详见 `format.md` 的"前向兼容"。

**3. 可能被追问的问题 + 要点**

- **Q：如果不剥离草稿头会发生什么？**
  A：草稿头会作为**正文的一部分**写进 `.gmd`，破坏格式；并且因为正文多了一行注释，`textHash` 与用户"真正想写的正文"不一致，校验 4 永远失败、用例 18 不可达。这是 PLAN 标为 P0 的原因。
- **Q：五道校验的顺序能不能换？**
  A：不能随意换，且**执行顺序不是编号顺序**：实际是 **①②⑤③④**。**步骤 0 必须最先**（它定义了"新正文"，后面所有校验都基于它）；接着 ① 正文非空、② `base_rev`（编号是 §4.6.2 的闸门号，② 在步骤 0 内一起做）；然后 ⑤ 范围存在性、③ dirty —— 这两道共用**同一次**目标来源读取（`readSourceForCommit` 一次拿到文本，越界看行数、dirty 看范围 hash），先判更基础的"范围是否真的存在"；最后 ④ 内容确有变化。**为什么 ③ 必须在 ④ 之前**：先告诉调用方"来源脏、先去提交"比"内容没变"更贴近根因，也避免它在脏来源上反复生成草稿。
- **Q：既然是"追加版本"，为什么同一份草稿第二次提交会被拒？**
  A：第一次提交后，活动版本的 `text_hash` 已等于草稿正文的 hash ⇒ 第二次提交命中校验 4"内容未变化"。这**是正确行为**：没有新内容就不该造无效版本。演示 2 里刻意展示过这一点。
- **Q：`--allow-dirty` 会不会让"不伪造正式版本"失效？**
  A：不会。默认（不加 flag）严格拒绝；加了 flag 也**不是伪造**——新版本 `commit` 仍记录真实 `HEAD`、`src_hash` 仍按当前工作区实测，并**在 `note` 与审计输出里明示"基于未提交来源"**。即"诚实标注的受控写回"，正是题面阶段 4 所列的能力。
- **Q：写 `.tmp` 用什么文件名？会不会和别的写操作撞车？**
  A：`<repo>/<doc>.tmp`，紧邻目标文件（同一目录 ⇒ 同一文件系统 ⇒ `rename` 才是原子的）。本题是单进程 CLI，不存在并发写同一文档的情形；若将来要做并发，需改成带随机后缀的临时名 + 加锁。
- **Q：为什么 `commit` 之后立刻 `read` 会变回 `ok`？**
  A：因为新版本的 `src_hash` 是用**当前工作区**的来源内容实测的，且新正文的 `text_hash` 也已写入。于是步骤 0、3、4 全部通过 ⇒ `ok`。这正是阶段 3"闭环"的收尾断言。
- **Q：来源被**截断**（文件还在，但引用到的那几行没了）时，`commit` 会怎么写？**
- **Q：来源被**截断**（文件还在，但引用到的那几行没了）时，`commit` 会怎么写？**
  A：**缺省拒绝，退出码 4**，理由"引用范围 A-B 已不存在（来源现有 N 行）"。不能照写的原因同"来源文件被删"那条：`src_hash` 必须由"当前来源文本 + range"算出，而越界 range 会算出**空串哈希**；写进去就得到一个"引用目标不存在却自证一致"的版本，read 随即判 `ok`。这正是复核时实测到的 P0：**修复前**"截断 → 重写 → commit → read"确实返回了 `ok`，而文件里根本没有那几行。现在两道闸（判定侧 3.5 + 写回侧校验 5）都拦（用例 24 / 25）；要真写回，就用 `--path`/`--range` 把引用改指到仍存在的范围。
- **Q：`error` 档"必须重写"，重写完怎么才能写进去？**
  A：用 `--path` / `--range` **重新绑定引用**（§4.6）。旧来源已消失时，光重写正文没用 —— 校验 5 会拿旧 range 去量新文本，必然越界 ⇒ 拒写（码 4）。改指到仍存在的来源之后闭环就走完了：`commit --block b1 --path src/conf.ts --range 9..13` ⇒ 新版本 `rev+1`、`read` 回到 `ok`（用例 28）。**关键约束**：新版本记新 `(path, range)`，`hist` 里旧版本的 `path`/`range` **不被改写** —— 历史只追加，这也是"能追问来源变化过程"的可信基础。
- **Q：重绑定会不会变成"随便改个指向就洗白"的后门？**
  A：不会，新来源不过三关就拒：① **存在性**（文件不在 ⇒ 码 4）；② **位置合法且范围存在**（`l0 ≤ l1`、`1 ≤ l0`、`range[1] ≤ 来源行数` ⇒ 否则码 4）；③ **dirty 闸门**（新来源范围内有未提交修改 ⇒ 默认码 4，除非 `--allow-dirty`）。`--path` 还必须落在仓库内（否则码 1）。用例 29 把这四条边界全覆盖了。语义上这也不是"洗白"：它记录的是**真的换了引用目标**，而且 `text_hash` 与 `range` 都按当前仓库实测，历史里还留着旧绑定，审阅者一眼能看出这块改指过。
- **Q：如果来源文件在 `edit` 之后被删掉了，`commit` 会怎么表现？为什么不是"照常写入"？**
  A：**拒绝，退出码 4**，理由为"来源文件已不存在，无法记录新版本的来源信息: `<path>`"。不能照常写入的原因：新版本必须记录 `src_hash` 与 `commit`，而 `src_hash = hashRange(当前来源文本, range)` 需要来源文件真实存在；阶段 1–3 又**不做符号/选区级引用**，`range` 只能沿用旧范围，无法改指他处。所以这是一个**无法成立**的写回。**为什么码是 4 而不是 1 或 5**：码 1 是"参数/用法错误"（参数没错）、码 5 是"环境错误"（git 好用、仓库正常），这属于 §4.9 的"写回被拒"。**为什么这是个真问题**：修复前这里是裸 `ENOENT` 冒泡 ⇒ 被兜底成码 1，AI 据码分支必然走错；而且这条路径恰好对应题面点名的 `error` 之一（"文件没了 ⇒ 必须重写"）。**恢复路径**：把来源恢复回去，同一条草稿即可写入（有回归用例覆盖）。
