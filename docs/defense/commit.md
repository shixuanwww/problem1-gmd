### 模块：写回闸门 `src/commit.ts`

**1. 这段在干什么（一句话）**
`gmd commit` 在把"新正文"写回 `.gmd` 之前，先**剥离草稿头**、跑**四道校验**（任一不过则拒绝、退出码 4），通过后重算来源信息、`hist` 追加新版本、用**原子写**落盘。

**2. 关键设计决策 + 为什么这么做**

- **步骤 0 先做：剥离并校验草稿头，定义"新正文"。** 若输入首行是 `<!-- gmd:draft … -->`，丢弃该行并解析 JSON；`doc`/`block`/`base_rev` 与实参或当前状态不符即拒绝。**这一步是必需的**：不剥离的话，① 草稿头会进 `.gmd` 正文、污染格式；② `text_hash` 永远对不上，"内容未变化"校验与用例 18 永远不可达。后续所有 hash/比较/写回**一律针对"新正文"**。
- **四道校验**（顺序即优先级）：
  1. **正文非空**（`trim()` 后非空）；
  2. **base_rev 匹配**（草稿基于当前活动版本）—— 防止覆盖别人的改动；
  3. **dirty 闸门** —— `judgeBlock(...).dirty === true` 且未加 `--allow-dirty` ⇒ 拒绝"来源存在未提交修改，默认拒绝写入"（题面硬约束 5："不伪造正式版本"）；
  4. **内容确有变化** —— `textHash(新正文) === 当前 text_hash` ⇒ 拒绝"内容未变化"（避免造无效版本）。
- **`--allow-dirty`（阶段 4·1）**：显式放行 dirty 写回，但必须① 在审计输出（stderr）显著标注"此版本基于未提交来源"，② 新版本 `note` 写 `based_on_dirty`。做到"可控 + 可追溯"。
- **通过后 `range` 沿用它记录的旧范围**：阶段 1–3 不做符号/选区级引用（那是阶段 4）。`commit` 只重算 `commit`（`git rev-parse HEAD`）与 `src_hash`（`hashRange(当前文件文本, range)`，**复用 gitrepo 的唯一实现**）。
- **原子写：写 `.tmp` → `rename`**。`rename` 在同一文件系统内是原子的，避免"写到一半崩溃 ⇒ 半截 `.gmd`"。测试专门验证 `.tmp` 不残留（`existsSync(doc+'.tmp') === false`）。
- **只改目标块**：`serializeGmd` 只替换该块区间，其它块与块外文本原样保留（`hist` 用 `[...b.hist, version]`，**只追加**）。

**3. 可能被追问的问题 + 要点**

- **Q：如果不剥离草稿头会发生什么？**
  A：草稿头会作为**正文的一部分**写进 `.gmd`，破坏格式；并且因为正文多了一行注释，`textHash` 与用户"真正想写的正文"不一致，校验 4 永远失败、用例 18 不可达。这是 PLAN 标为 P0 的原因。
- **Q：四道校验的顺序能不能换？**
  A：不能随意换。**步骤 0 必须最先**（它定义了"新正文"，后面所有校验都基于它）；**dirty 闸门在"内容未变化"之前**——先告诉用户"来源脏、先提交"比"内容没变"更贴近根因。`base_rev` 校验也在内容校验之前（版本冲突优先于内容重复）。
- **Q：既然是"追加版本"，为什么同一份草稿第二次提交会被拒？**
  A：第一次提交后，活动版本的 `text_hash` 已等于草稿正文的 hash ⇒ 第二次提交命中校验 4"内容未变化"。这**是正确行为**：没有新内容就不该造无效版本。演示 2 里刻意展示过这一点。
- **Q：`--allow-dirty` 会不会让"不伪造正式版本"失效？**
  A：不会。默认（不加 flag）严格拒绝；加了 flag 也**不是伪造**——新版本 `commit` 仍记录真实 `HEAD`、`src_hash` 仍按当前工作区实测，并**在 `note` 与审计输出里明示"基于未提交来源"**。即"诚实标注的受控写回"，正是题面阶段 4 所列的能力。
- **Q：写 `.tmp` 用什么文件名？会不会和别的写操作撞车？**
  A：`<repo>/<doc>.tmp`，紧邻目标文件（同一目录 ⇒ 同一文件系统 ⇒ `rename` 才是原子的）。本题是单进程 CLI，不存在并发写同一文档的情形；若将来要做并发，需改成带随机后缀的临时名 + 加锁。
- **Q：为什么 `commit` 之后立刻 `read` 会变回 `ok`？**
  A：因为新版本的 `src_hash` 是用**当前工作区**的来源内容实测的，且新正文的 `text_hash` 也已写入。于是步骤 0、3、4 全部通过 ⇒ `ok`。这正是阶段 3"闭环"的收尾断言。
