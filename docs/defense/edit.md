### 模块：草稿 `src/edit.ts`

**1. 这段在干什么（一句话）**
`gmd edit` 为指定片段生成一个草稿文件（`<!-- gmd:draft … -->` 头 + 当前正文），并导出 `stripDraftHeader` 供 `commit` 剥离草稿头、定义"新正文"。

**2. 关键设计决策 + 为什么这么做**

- **草稿 = 草稿头行 + 正文，不含任何提示语。** 对应 `docs/notes-plan-conflicts.md` §1.1：PLAN 示例里的那行中文提示若真写进去，会被 `commit` 当成正文、污染 `.gmd` 且让用例 18（原样提交应"内容未变化"）永不可达。所以这里只写"头 + 正文"。
- **草稿写在 `<repo>/.gmd/tmp/`，且判定从不读它。** 题面禁止"旁车文件/索引/数据库/文件名"承载元数据；草稿是**临时的、可删的、不参与判定的**，因此不违反 —— 它是"人/AI 改写正文"的工作台，而不是元数据源。
- **草稿路径带去碰撞后缀**：`<doc 相对路径的分隔符→下划线>-<sha256(文档绝对路径)前8位>-<block>.draft.md`。只用文档相对路径会**同名覆盖**（不同仓库里都有 `docs/api.gmd`）；加绝对路径摘要后缀即可区分。目标已存在则**覆盖并打印提示**，不静默追加编号（PLAN §4.6.1）。
- **`stripDraftHeader` 是 `commit` 的"步骤 0"**：识别首行 `<!-- gmd:draft `、解析 JSON、`doc/block/base_rev` 三字段校验（防止把 b2 的草稿误提交到 b1、或基于旧版本覆盖别人的改动）。它同时返回 `headerError`，把"缺字段 / JSON 非法 / 缺尾标记"三种情况显式交给调用方拒绝（码 4）。
- **`edit` 对 `error` 片段也放行**：题面"error 时必须重写"，所以 `edit` 不看 `severity` 是否 error。

**3. 可能被追问的问题 + 要点**

- **Q：草稿文件算不算题面禁止的"旁车文件"？**
  A：不算。题面禁的是"依赖旁车文件来判断语义"。本实现**判定从不读草稿**，删掉草稿后仅凭 `.gmd` 仍能完整判断（这正是测试覆盖的：删草稿不影响 `read`）。草稿只是编辑过程中的临时载体，`commit` 后即可删。
- **Q：为什么要校验 `base_rev`？**
  A：防止**基于旧版本的草稿覆盖新版本**：AI 拿到 `edit` 的草稿后可能隔了一会儿才提交，其间别人（或另一个 AI）已提交过一版。`base_rev ≠ 当前 rev` 直接拒绝（码 4），提示"草稿基于旧版本 rev=N，当前为 M"。
- **Q：`doc`/`block` 也校验，防的是什么？**
  A：防"张冠李戴"—— 把 `b2` 的草稿内容提交到 `b1`。`doc` 校验则防跨文档误投。
- **Q：`nowIso()` 为什么把毫秒去掉（`replace(/\.\d{3}Z$/, 'Z')`）？**
  A：保证 `at` 字段格式稳定（秒级 ISO8601 UTC），与 fixture 的固定时间戳风格一致，也让输出可读、可 diff。时间只用于展示与排序，不参与判定。
- **Q：草稿头 JSON 需要 `--` 转义吗？**
  A：草稿头本身就是 HTML 注释。字段值（`doc`/`block`）一般不含 `--`，但为稳妥，`renderDraftHead` 也应走 `escapeDashes`（与 `.gmd` 元数据同规则）。这样即便路径里含 `--` 也不会提前闭合注释。
