### 模块：解析 / 序列化 `src/format.ts`

**1. 这段在干什么（一句话）**
把 `.gmd` 文本严格解析成 `{doc, blocks, raw}`（任何异常都抛带行号的 `GmdFormatError`），以及把片段重新序列化回文件（只替换块区间、块外逐字节保留）。

**2. 关键设计决策 + 为什么这么做**

- **HTML 注释承载元数据**：标准 Markdown 渲染器忽略 HTML 注释 ⇒ 阅读体验不被破坏（题面要求），元数据又是纯文本、可 diff、可手改。这是整个格式的地基。
- **`--` 转义只在序列化时做、只对 JSON 字面量**（`escapeDashes`：`json.replace(/--/g,'\\u002d\\u002d')`）：HTML 注释内出现 `--` 会**提前闭合**，把后面的内容挤出注释、整个格式损坏。选择在**序列化**时统一转义，而不是解析时处理，是因为注释一旦被提前闭合，解析器看到的就已经是残缺文本，**无法可靠还原**。
- **一个正则扫全部标记**（`MARKER_RE`，JSON 允许跨多行），再按出现顺序做状态机：这样"未闭合 / 嵌套 / 多余闭合"三种损坏都能在**同一次线性扫描**里检出并定位行号。
- **围栏代码块内的标记字面量不算标记**（`scanFenceSpans`）：先按行扫出**已闭合**的 ```/~~~ 围栏区间，落在区间内的 `<!-- gmd:… -->` 一律跳过。**为什么必须做**：题面要求"普通 Markdown 阅读体验不应被明显破坏"，而一份**讲 .gmd 格式本身**的文档必然会在代码块里写出 `<!-- gmd:block … -->` 这类示例；不豁免的话，合法文档会被判成"片段嵌套 / 未闭合"（退出码 2）—— 工具连自己的文档都写不了。**为什么只认"已闭合"的围栏**：正文里一个没配对的围栏（CommonMark 允许，但通常是笔误）不应该把后面**真正的**块标记一起吞掉，否则一个笔误就从"解析失败"升级成"结构全乱"。
- **来源路径必须是仓库内的相对正斜杠路径**（`validateVersion` 调 `gitrepo.isRepoRelativePath` —— **全仓库共用同一份判定**，不在这里另抄）：拒绝绝对路径 / 盘符 / 反斜杠，也拒绝 `..`、`.` 与空段。**这不是洁癖，是安全闸门**：`.gmd` 是给 AI 读的、可能由模型生成；若放任 `path: "../../x"`，`path.resolve(repo, path)` 会解析到仓库之外，`gmd read` 就把仓库外任意文件的内容当"来源当前内容"打印出来（任意文件读取）。闸门有两道：解析期（本文件，报格式错、码 2）+ 取绝对路径时（`gitrepo.resolveInRepo`，`startsWith(root + sep)` 兜底）。
- **`normalizeBlockBody` 是唯一实现**：解析（`parseGmd`）与写回（`commit`）共用"归一化换行 + 去掉首尾各一个换行"。不共用的话，`edit → commit` 往返会凭空多/少空行，`text_hash` 与文件外观都会漂移。
- **`serializeGmd` 只替换块区间**：先扫出每个块的字节区间 `[open.start, close.end]`，再把新块按原顺序填进去，区间之间的文本**原样拼接**。这样 `commit` 天然满足题面"块外文本逐字节不变"（测试用例 17）。
- **解析绝不宽容**：任何异常都 `throw`，不"跳过坏块继续"。题面硬约束 4 明确"格式损坏必须报错，绝不判为可用"。

**3. 可能被追问的问题 + 要点**

- **Q：如果作者在正文里（块内）写了一段包含 `<!-- gmd:block` 的代码示例呢？**
  A：**围栏代码块里的不算标记** —— 只要那段示例写在 ```/~~~ 围栏内（正常写文档都是这样），文档完全合法、可读写回。围栏**之外**的裸标记仍按真标记解析（这是 `.gmd` 的定义），所以"正文里逐字写一个未围栏的 `<!-- gmd:block`"依旧会破坏格式。取舍是：既保住"讲格式的文档能自洽"，又不用给正文引入转义层。
- **Q：围栏豁免会不会被正文利用来"藏"标记、从而伪造结构？**
  A：不会。豁免是**保守方向**的：它只会让本该是字面量的东西**不被**当成标记（少识别），不会凭空造出块。要造块必须在围栏**外**写真标记 —— 那本来就是这个格式的语法，`hist` 的 `text_hash` / `src_hash` 与 `rev` 连续性校验照旧约束它（手改正文不追加版本 ⇒ 步骤 0 直接 `error`）。
- **Q：为什么 `..` 要拦？CLI 里 `path.resolve` 不是能处理吗？**
  A："能处理"正是问题：`path.resolve(repo, '../../secret')` 会老老实实解析到仓库外，然后 `readFile` 就把它读出来当"来源当前内容"回显给 AI。所以要在**解析元数据时**就拒绝（`..` / `.` / 空段 / 绝对路径 / 盘符），而不是指望后续函数自觉。`gitrepo.resolveInRepo` 再做一次 `startsWith(root + sep)` 兜底，防止将来有新的调用点绕过格式层。回归用例：用例 27（`../outside.ts`、`src/../../outside.ts`、`/etc/hosts`、`C:/Windows/win.ini`、`src//kv.ts` 全部码 2）。
- **Q：为什么 `serializeGmd` 要求"原文片段数与待写片段数一致"？**
  A：`commit` 只改**内容**、不增删片段（题面"片段级独立"）。数量不一致说明调用方误用（比如把解析结果改了结构），此时抛错比默默产出错文件安全。
- **Q：块正文"去掉首尾各一个换行"——为什么是"各一个"而不是 `trim()`？**
  A：为了**可逆**。`renderBlock` 写盘时是 `块头\n正文\n块尾`，解析时"各去掉一个换行"正好还原正文；若用 `trim()`，正文里**有意的**前导/尾随空行会被吃掉，往返不幂等。而 hash 计算里另有 `textHash` 会 `trim()`，判定不受这些空行影响。
- **Q：`parseJsonObject` 为什么先要求是"对象"再校验字段？**
  A：`JSON.parse` 可能返回数组/数字/`null`，若不先拦住，后续 `obj.gmd` 之类访问会在数组上静默变成 `undefined`，导致"字段缺失"被误报成"格式损坏"的**另一种**错误。先判对象，报错更准。
- **Q：文件头的 BOM 怎么处理？**
  A：`parseGmd` 与 `stripDraftHeader` 都会**先剥掉首个 BOM**（`\uFEFF`），避免 BOM 让"第一个非空内容是 `gmd:doc`"误判失败。写盘侧统一 `\n`，不写 BOM。
